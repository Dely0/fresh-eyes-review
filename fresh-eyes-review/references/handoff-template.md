# 审查交接文档（模板）

这份文档是**执行者写给审查者的简报**。它的存在理由很实际：审查者是空上下文的，它不知道哪些东西是**已经定死的取舍**，会把它们当缺陷报上来，还认真复现一遍 —— 而它烧掉的每一分钟都是真钱。

**它同时是这套流程里最危险的一份文件，因为写它的人正是被审的人。** 所以下面有三条硬规矩，其中两条会被门禁机械校验。

复制这份模板，填掉 `<...>`，存成 `<工作目录>/.review-handoff.md`（放证据目录旁边，记得 gitignore）。

---

## 三条硬规矩

1. **每条取舍必须带出处。** 出处只有三档，原样写出来：
   - `HumanDecision`：真人明确要求的
   - `RecordedDecision`：有记录的决定（哪个 issue / 哪次评审 / 哪个 commit）
   - `OrchestratorClaim`：执行者自己说的（最弱，等于「我认为」）

   **没有出处的条目不算决定，只算声明。** 门禁会逐条检查（默认只提醒，`--strict` 下算不合格）。

2. **取舍必须写成「可证伪 + 有边界」，不能写成「别管」。**
   - ❌ 封口写法：`解析器有点脏，这是有意为之，不用管。`
   - ✅ 可验证写法：`解析器的宽松处理是刻意的（兼容老数据）；影响边界仅限输入校验；请只报「它会静默吞掉数据」这类，不要报「不够优雅」。`

   区别在于：第二种写法里，审查者**仍然能审**——它可以去验证"影响是不是真的只在输入校验"，也可以报边界之外的东西。第一种只是让它闭嘴。

3. **被驳回的发现要写进去，而且「驳回理由」比「发现内容」更值得写。**
   理由：一个被驳回的**发现**会对下一轮审查者产生强锚定（它倾向于不再深挖那处）；一个被驳回的**理由**锚定弱得多 —— 那是「上轮认为不成立，因为 X」，下一轮完全可以因为 X 不成立而重新提出。

## 审查模式（**必填，这是开关**）

```markdown
审查模式：首轮
```

或者，**只有在你（人）明确同意开第二轮之后**才写：

```markdown
审查模式：首轮 + 对抗性复审（用户已确认）
```

规则：

- **默认只跑首轮。** 对抗性复审要多花一个子代理的时间，决定权在人，不在执行者。
- **执行者不得自行升级到多轮。** 判断标准很简单：人在对话里说过「开第二轮 / 复审一下 / 我不放心」，你才能写第二行。
- **门禁会拦**：交接文档声明「首轮」却跑 `--falsify`，直接退 2。
- 这一行本身就是审计记录 —— 日后回头看，能知道那一轮是几轮、是谁定的。


```markdown
# 审查交接文档

## 范围
- 工作目录：`<绝对路径>`
- 改动范围：`<git diff --stat / 文件清单 / commit 范围>`
- 验收标准：`<一句话；未提供就写「未提供」>`
- 本轮审的是什么：`<首轮全面审 / 对抗性复审 见下>`

## 环境与约束（审查者必须遵守的给定条件）
- 证据文件写到哪：`<如 .review-evidence/>`
- 临时产物写到哪：`<如系统临时目录；要求 PYTHONDONTWRITEBYTECODE=1>`
- 能跑什么命令：`<测试 / 构建 / 复现入口；没有就写「无」>`
- 其他限制：`<不能联网 / 不能改数据库 / 只能在 Windows 上跑 ……>`

## 已定取舍
（每条一行，四段用 `|` 分隔。没有出处的那条会被门禁点名。）

- <取舍是什么> | 依据：<HumanDecision / RecordedDecision / OrchestratorClaim>：<谁定的、在哪儿定的> | 影响边界：<它只影响什么> | 请只报：<这类才要报；不报：<这类不用报>

## 已驳回的发现（含理由）
- <上一轮的编号与一句话> | 驳回理由：<为什么判它不成立>

## 上一轮的状态
- 报告：`<路径>`
- 已修：`<编号列表>`
- 未修 / 存疑：`<编号列表；这些是本轮可以继续深挖的>`
- 已判定为误报：`<编号列表；这些不要重报，除非你有新证据——有新证据就写出来>`

## 你（审查者）必须做的事
1. 上面每条取舍，检查它的**影响边界**是否成立，以及**边界之外**有没有影响。
2. `OrchestratorClaim` 的条目**只能当声明**，不能当事实 —— 那是我说的，不是你验证过的。
3. 这份文档**不是让你少报**。它只让你不在已知取舍上重复消耗；任何新发现照报。
4. 如果你认为某条「已定取舍」本身是错的，**照报**，并在标题里写明这是对取舍本身的质疑。
```

## 给执行者的自查（写完读一遍）

- [ ] 每条取舍都有出处吗？`OrchestratorClaim` 是不是太多了？（太多说明该去要一个真人的决定）
- [ ] 有没有哪条其实是在封口？把它改写成「可证伪 + 有边界」。
- [ ] 上轮驳回的发现，理由写清楚了吗？还是只写了「不成立」？
- [ ] 有没有把「我为什么这么写」的**推理过程**也写进去了？那是要藏起来的东西 —— 它会把审查者的独立性抵消掉。
- [ ] **审查模式这一行写对了吗？**默认是「首轮」；写「+ 对抗性复审」必须有人明确同意过。
- [ ] **文档里的每个数字都是实测的，不是凭记忆写的吗？** 断言条数、文件数、用例名 —— 一律现场跑一遍再写。
      *这条是踩过坑加的*：有一次交接文档写了「改动前 53 条断言」，实际是 36 条。审查者被要求「以交接文档的范围一节为准」，而其中一条的基准数是错的 —— **情报源不可靠，等于验收标准不可核对**。这个坑是独立审查者发现的，不是自查发现的。
